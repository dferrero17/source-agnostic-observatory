\begin{abstract}
An urban observatory is worth as many indicators as it can actually take in, and
that number is usually small. Every feed, a statistics-office API here, a town
spreadsheet there, an occasional CSV, arrives in its own shape and needs its own
extraction code that somebody writes and then keeps alive. We describe \sys{}, a
smart city observatory in production whose intake layer removes that per-feed
labour: a non-technical user registers a source through a form, and the platform
then writes, runs, and maintains the extraction code on its own, whatever the
source looks like. The design idea is to treat each source's wrapper as a
self-managing component driven by a single autonomic control loop, in the
monitor--analyze--plan--execute--knowledge (MAPE-K) sense, whose actuator is a
large language model that emits and revises the wrapper's code. Three behaviours
follow from that one loop. The model writes a wrapper by completing a fixed
template from the source's metadata and a small sample, querying the live
endpoint first when the source is an API. The wrapper is then launched,
supervised, and check-pointed as an isolated process with nobody watching. And
when it later throws, the loop returns the crash trace to the model and ships a
corrected version. Over \deploymentDays{} days the platform stood up
\nWrappers{} wrappers across API, spreadsheet, and CSV feeds and gathered
\nDataPoints{} measurements. Of the \nRetried{} wrappers (\pctRetried\%) that
crashed and were auto-repaired, \nRecovered{} ended in a healthy state and 32
went back to delivering data, each repair taking a median \healLatencyMedian{}\,s;
the entire stack fits in roughly 1.5\,GiB. The pattern has a clear edge, too:
defects in the generated code and a source's formatting quirks lie within the
loop's reach, whereas spent quotas, wrong credentials, and badly set limits are
environmental and lie beyond it.
\end{abstract}

\section{Introduction}
\label{sec:intro}

The indicators a city cares about already exist somewhere, but rarely in a form a
dashboard can read. Water and air quality, energy use, mobility counts, overnight
stays, and cultural attendance each come from a different publisher, a statistics
office, a town hall, an industry body, in whatever encoding that publisher happens
to use: a REST endpoint one day, an Excel workbook or a CSV dump the next, each
with its own column names, date conventions, language, and ways of failing. Making one of these feeds usable has meant writing
a dedicated extraction wrapper and then nursing it through every upstream change,
and that recurring per-source cost is the reason mediator-style integration has
resisted scaling for three
decades~\cite{wiederhold1992mediators,kushmerick2000wrapper,lerman2003wrapper}.
An observatory that can only fund a fixed handful of wrappers describes not its
city but whichever feeds an engineer had time to wire.

We call an intake layer \emph{source-agnostic} when onboarding a feed costs no
bespoke code: a domain user completes a registration form, and the platform
carries the source from there through extraction and continued upkeep without
further human work. This paper reports \sys{} (anonymized for review), a smart
city observatory running for a European region, where source-agnostic intake is
obtained by making each wrapper an \emph{autonomic} element in the sense of
Kephart and Chess~\cite{kephart2003vision}: a component that manages itself
through a closed loop over its own lifecycle. What is unusual is the actuator.
A conventional autonomic manager adjusts the knobs of a fixed component; ours
asks a large language model (LLM) to write the component's code, and to rewrite
it after a failure.

We organize the wrapper's three self-* behaviours as the
monitor--analyze--plan--execute loop over shared knowledge (MAPE-K) of the
autonomic-computing blueprint~\cite{ibm2005blueprint,huebscher2008autonomic}.
At registration, \emph{self-generation} (Section~\ref{sec:gen}) plans the
artifact: the LLM completes a fixed template from the indicator's metadata and a
data sample, interrogating a live API through a controlled fetch tool before it
writes anything. \emph{Self-deployment} (Section~\ref{sec:deploy}) is the execute
step that runs unattended: each wrapper is an isolated process the platform
starts, watches, check-points, and resumes from per-wrapper watermarks after any
restart. \emph{Self-healing} (Section~\ref{sec:heal}) is the loop closing on a
live artifact: a crash is detected, the termination is classified, the model
re-plans from the captured trace, and the corrected wrapper goes back out.

An earlier paper by the same group examined this platform's crash-triggered
repair in isolation~\cite{anonprior}.\footnote{Cited anonymously; identifying
details are withheld for double-blind review. We disclose the overlap here and
to the program committee.} The present work reframes the system as a
source-agnostic autonomic manager, brings its self-generation and
self-deployment loops into the same account, and analyzes where the manager's
authority ends. Three contributions follow. We set out the observatory's
architecture and its one narrow contract: every source is reduced to a stream of
normalized $(\textrm{timestamp}, \textrm{value})$ points by a wrapper the
platform owns end to end. That contract is what makes intake source-agnostic
(Section~\ref{sec:arch}). We then unify the three self-* behaviours as a single
autonomic manager over a shared knowledge base, assign each its MAPE-K role, and
position it against autonomic computing, LLM-based code generation and repair,
and wrapper maintenance (Section~\ref{sec:selfstar}; related work in
Section~\ref{sec:related}). Finally we measure a live \deploymentDays{}-day run
rather than a benchmark, using a pre-automation reference period and a fault
analysis that fixes the manager's scope of control
(Section~\ref{sec:results}).\coderepo

\section{Background and Related Work}
\label{sec:related}

\subsection{Smart city and tourism observatories}
The smart-tourism literature has long argued for destination-scale data
infrastructure~\cite{gretzel2015smart,buhalis2013smart} and has codified the
indicators worth tracking through schemes such as ETIS~\cite{ec2016etis}, while
field reports describe patchy uptake~\cite{modica2018assessment} and dashboards
assembled mostly from warehouses and surveys~\cite{fuchs2014big}. A recurring
finding in evaluations of smart-destination initiatives is that the binding
constraint on sustained monitoring is getting the data in at
all~\cite{ivarsbaidal2021measuring,ivarsbaidal2023sustainable}. These accounts
say little about how intake is actually built. Our claim is that the intake
layer, specifically its ability to absorb arbitrary sources, sets the ceiling on
how many indicators an observatory can keep alive, and we report one such layer
from production. The deployment happens to be a tourism observatory, but nothing
in the design depends on that: it needs only heterogeneous sources and a shared
time-series target.

\subsection{Autonomic computing and self-* systems}
Autonomic computing proposed self-managing components with closed control loops
as the response to operational complexity~\cite{kephart2003vision}, structured
as a monitor--analyze--plan--execute cycle around a shared knowledge base
(MAPE-K)~\cite{ibm2005blueprint}, and later surveys catalogue its self-* property
families~\cite{huebscher2008autonomic}. \sys{} applies that blueprint to data
wrappers, but swaps the actuator: instead of tuning a fixed component's
parameters, the manager regenerates the component's source code through an LLM,
so configuration becomes synthesis and recovery becomes repair.

\subsection{LLMs for code generation, repair, and extraction}
Language models now write runnable programs from prose~\cite{chen2021evaluating},
and automated repair has moved toward LLMs as well~\cite{xia2023automated}.
Several systems close a feedback loop around the generated code, whether through
self-critique~\cite{madaan2023selfrefine}, episodic
reflection~\cite{shinn2023reflexion}, or conditioning on execution
results~\cite{chen2024selfdebug}, though the benefit of self-repair is
inconsistent~\cite{olausson2024selfrepair}. On the data side, Evaporate
established that synthesizing extraction code is cheaper at scale than calling a
model per record~\cite{arora2023evaporate}, AutoScraper builds reusable scrapers
with an agent~\cite{huang2024autoscraper}, and both prompted~\cite{narayan2022wrangle}
and fine-tuned~\cite{zhang2024jellyfish} models handle textbook preprocessing
steps. Our planner reuses these ideas; what differs is the signal and the unit.
The signal that prompts a plan is a crash from production rather than a failing
unit test, and the plan rewrites the entire managed artifact instead of editing a
faulting line. We do not claim novelty in the code generation itself; the
contribution is the autonomic-systems framing around it and the longitudinal
production evidence, neither of which the systems above set out to provide.

\subsection{Wrapper induction, maintenance, and ETL automation}
Early wrapper induction derived extraction rules from labelled
examples~\cite{kushmerick2000wrapper}, later systems learned them without
supervision from structural regularities~\cite{crescenzi2001roadrunner}, and the
tooling has been surveyed at length~\cite{laender2002brief,ferrara2014web}.
Keeping a wrapper working as its source drifts, by spotting the break and
re-deriving the rules, was identified as a distinct problem from the
start~\cite{kushmerick2000verification,lerman2003wrapper}. ETL pipelines,
meanwhile, have mostly been designed by hand rather than
generated~\cite{vassiliadis2002conceptual,vassiliadis2009survey}, with automation
reaching adjacent pieces such as schema matching~\cite{rahm2001survey},
large-scale curation~\cite{stonebraker2013tamer}, and
wrangling~\cite{furche2016wrangling}. \sys{} folds both the initial derivation and
the later re-derivation into LLM code generation, which reaches past
template-structured pages to arbitrary APIs and workbooks, and it targets exactly
the slice an indicator platform needs: pulling one series from one source into one
normalized schema.

\section{A Source-Agnostic Observatory}
\label{sec:arch}

\Sys{} runs as a set of containerized services, user, knowledge-base,
data-collector, resource, and indicator (all Python and FastAPI), reached through
an nginx gateway and fronted by a React dashboard. Control traffic and data
traffic ride separate RabbitMQ brokers, and the resource and indicator services
each keep their own MongoDB store. The pipeline appears in
Figure~\ref{fig:arch}.

\begin{figure}[t]
\centering
\resizebox{\columnwidth}{!}{\input{fig_arch}}
\caption{Data path through \sys{}. Wrappers are generated, launched, and repaired
by the resource service; the points they emit cross two brokers on their way to
the indicator store and the dashboard.}
\label{fig:arch}
\end{figure}

Source-agnostic intake rests on one deliberately thin interface. Regardless of
where its data comes from, a wrapper emits point batches $\{(x,y)\}$ in which $x$
is an ISO~8601 timestamp and $y$ a floating-point value; the code above that
interface is generated per source, and everything below it is shared, fixed
plumbing. Registration is a web wizard: the user either uploads a spreadsheet or
CSV file or points the platform at an API endpoint and its credentials, and
supplies the indicator's metadata, name, domain, unit, periodicity, and a
description. The resource service then takes ownership of that wrapper for life.
On the data side, the collector checks each batch against the interface, keeps
the most recent batch per wrapper, and passes valid points to the control broker;
there the resource service translates wrapper identifiers into durable resource
identifiers, and the indicator service persists the segments, stitches them into
ordered series, and answers the dashboard's queries. Because source type is one
argument to a single generation routine rather than a code path of its own, the
same machinery extends to a new kind of feed without new code.

\section{Self-* Wrappers as an Autonomic Manager}
\label{sec:selfstar}

Each wrapper is the element a single autonomic manager looks after. That element
is the generated artifact plus the state that travels with it: the wrapper's
code, its execution watermarks, its retry counter, and its status. The platform
turns the MAPE-K loop~\cite{ibm2005blueprint} on that element, watching process
state, classifying how a process ended, planning a fresh or corrected artifact,
and carrying the plan out by deploying it, all against a shared store of
knowledge (Table~\ref{tab:mapek}). The three self-* loops in
Figure~\ref{fig:selfstar} are what this decomposition yields. In every one of
them the actuator is the same pairing: an LLM that produces and revises code, and
a process supervisor that puts it into service.

\subsection{Shared knowledge}
\label{sec:knowledge}
What binds the loops into one manager, rather than three disconnected
mechanisms, is the knowledge they share. Some of it is fixed. The wrapper
template encodes the Section~\ref{sec:arch} contract as code, and a standing list
of fourteen hard rules captures lessons from earlier failures, among them: leave
the historical-backfill driver alone, invent no data, treat date ranges as
inclusive, keep timezone handling uniform, and read non-English dates such as
localized month names. Together these constrain what the planner is allowed to
emit. The rest is per-wrapper and changes at runtime: a pair of watermarks (the
earliest and latest timestamps sent) with a phase, a retry counter capped at
three, a timestamped execution log, and the stored wrapper document carrying its
metadata, source configuration, current code, and status. The generation loop
writes the first version of the code, the deployment loop reads and advances the
watermarks, and the healing loop reads the code and the log and writes a
successor. The rule list is the part that grows: each diagnosed failure can add a
constraint that every later plan must respect.

\subsection{Self-generation: planning a new artifact}
\label{sec:gen}
The model does not write code freely; it works inside a fixed wrapper class
(Figure~\ref{fig:gen}). Only a few methods are open to it, extraction
(\texttt{fetch\_external\_data}) and, for APIs, a windowed fetch and a polling
period, while the backfill driver, the message transport, the batching, and the
run loop are library code the prompt tells it not to touch
(Figure~\ref{fig:template}). Jinja2 assembles the prompt. Into it go the
indicator metadata, the source configuration, and a brief sample of the data:
the opening 20 lines of a CSV, 15 rows from each workbook sheet alongside the
sheet names, or a captured API reply. Alongside the sample sit the required
\texttt{\{x,y\}} output shape, the template, instructions specific to the source
type, and the rule list. When the source is an API, the same call hands the model a sandboxed
\texttt{fetch\_url} tool that returns up to 2500 characters of a live response; it
may use the tool as many as fifteen times to learn the response's nesting, its
field names, and which date filters the endpoint honours, rather than inferring
them from the URL. Request authentication is built into the headers by the
service from the declared scheme, so the model never handles it. A static check
gates deployment, parsing the file and looking for placeholders left unfilled;
a first failure earns one corrective prompt, a second sends the wrapper to
\texttt{error}. Nothing is executed as a test beforehand, so any runtime fault is
the healing loop's problem.

\subsection{Self-deployment: execute without an operator}
\label{sec:deploy}
Nothing about putting a wrapper into production needs a person. The resource
service runs each one as a separate operating-system process, passing the
wrapper identifier and source configuration on the command line and the broker
URL in the environment. The number of processes alive at once is held under a
semaphore (defaulting to 100), and a watchdog (defaulting to 3600\,s) caps any
single run. A file wrapper executes once and exits; an API wrapper first
back-fills history in size-adapting batches and then settles into polling at the
period its indicator's periodicity implies (hourly turns into 3600\,s, daily into
86\,400\,s), the loop living inside the process with no external scheduler. Output
leaves in batches of up to 1000 points. A monitor reads each process's state on a
30\,s cycle. Every wrapper keeps a low and a high watermark, its earliest and
latest emitted timestamps; after a restart it picks up from the high mark instead
of re-fetching, which keeps a relaunch from either duplicating or skipping points,
and the resume position is handed back through the environment. Above the
individual wrappers, a container updater pulls fresh service images into
production with no manual rollout. This execute step is what lets the other two
loops run on their own: generation produces a process to oversee, and healing
produces a replacement to relaunch and resume.

\subsection{Self-healing: the full loop on a live artifact}
\label{sec:heal}
Healing is where every MAPE-K stage shows up at once. The 30\,s monitor reads
each process's exit status (\emph{monitor}). An abnormal exit, in practice always
code~1, is separated from an idle watchdog kill and from a provider error during
generation, and only the first becomes a repair (\emph{analyze}). The plan is an
LLM call carrying the full crashed source, its captured stderr, and the final
twenty lines of stdout, with the instruction to return a complete corrected file
that preserves the class and addresses that particular traceback (\emph{plan});
for an API wrapper it may re-interrogate the endpoint through the same
\texttt{fetch\_url} tool, up to ten times. The returned file goes through the same
static check as a first generation, replaces the old file, bumps the retry
counter, and the process is relaunched and resumed from its watermarks
(\emph{execute}). The manager grants at most three repairs to any wrapper and
leaves the fourth-time loser in \texttt{error} for a person. Two things come from
treating the artifact, not a diff, as the unit of repair. The trigger is a live
exit code that may arrive weeks after generation, so the feedback carries the
source's real behaviour rather than a test author's guess; and because the plan
re-emits the whole wrapper, a repair can re-shape the extraction end to end
instead of touching one
statement~\cite{chen2024selfdebug,olausson2024selfrepair}.

\subsection{Scope of control}
\label{sec:scope}
Source-agnosticism then comes out of the manager rather than from any separate
component. One knowledge base and one set of loops cover API, spreadsheet, and
CSV feeds because source type is a parameter the template takes, so a new kind of
feed is absorbed simply by generating, deploying, and repairing its wrapper with
no human writing code. The same view marks the limit of the manager's reach.
Faults that live in the managed element, broken extraction logic and the
idiosyncrasies of a source's format, are inside its authority and are dissolved
by generation and repair; faults in the surroundings, a spent model quota, a
stale credential, a watchdog set shorter than a source's polling period, are
outside it. We return to that line in Section~\ref{sec:results} with the
production fault counts, and note that it is partly a design choice: some
``environmental'' faults, the poll-interval mismatch in particular, are values the
generator itself sets and could in principle be brought inside the loop.

\subsection{Self-healing effectiveness}
\label{sec:res-heal}
\nRetried{} wrappers, \pctRetried\% of the total and split 26 spreadsheet, 14
API, and 3 CSV, threw an uncaught exception while running and were taken up by the
repair loop, which shipped \nHealEvents{} redeployments; counted per wrapper, the
repair depth was \retryOnce{} at a single attempt, \retryTwice{} at two, and
\retryThrice{} at three. ``Recovery'' can be read three ways, and they do not
agree, so we keep them apart. Measured by recurrence, the same crash came back
after the last repair for exactly one of the 43, so 42 stayed crash-free.
Measured by final status, \nRecovered{} of 43 (\pctRecovered\%) closed in a
non-error state. Measured by output, 32 resumed sending data after their last
repair, 20{,}351 points, about an eighth of everything collected. The one wrapper
that burned all three attempts never stabilised; it shows a non-error status only
because its resource was deleted afterwards, and we do not score the deepest-retry
case as a win. The repairs themselves were fast and untouched by a person: a
median \healLatencyMedian{}\,s from crash to redeployment (quartiles 24.2 and
50.8\,s, 90th percentile \healLatencyPninety{}\,s, longest \healLatencyMax{}\,s
over the \nHealEvents{} events), up to 30\,s of which is the detection cycle. The
typical crash arrived 16.8\,s into a run, in the fetch-and-parse stage, and none
occurred while a poller waited idle.

The run also offers a pre-automation reference period. For the first 65 days no
repair loop was active (it first appears in the logs on 2026-03-19), and over
that stretch 36 crashes of this same exit class were simply left to die; we read
the comparison descriptively, since the early period differs in source mix and
load and is not a matched control. Two features of the timeline qualify the
healing counts. Thirty-one of the 50 repair events land on a single day, when a
credential fix set off a redeploy that restarted every wrapper together, so the
events are correlated and the pooled latencies above reflect that batch more than
50 separate failures. And since each relaunch overwrites the stderr file, a
triggering traceback survives only where the last run also crashed; for the
wrappers that recovered we infer the trigger from the fixes their code carries,
which means these counts describe the \emph{repairs} the model made rather than
independently observed causes. So read, a comment or guard pointing at a mended
defect shows up in 7 of the 43 crashed wrappers and in none of the 353 that never
crashed, and a timezone fix in 4 of 43 against 1 of 353.

\subsection{Repair case studies}
\label{sec:res-cases}
Four wrappers span the range. The causes in the first two are read off the fix,
the third has its exception quoted in the repaired file, and the fourth kept its
trace because it never recovered.

\subsubsection{Aware-versus-naive datetime comparison (API, healed)}
A yearly urban-waste API wrapper fell over 82\,s into its backfill while matching
timezone-aware dates from the source against timezone-naive window bounds. Its
repair brings both bounds to naive form before the comparison and downgrades an
empty fetch from an exception to a log line. Back in service after 34.7\,s, it
ran to completion with 596 points.

\subsubsection{Doubled date parameters (API, healed)}
An air-quality wrapper had been given an endpoint URL that already pinned a date
window; the generated code added a second one, and the server replied HTTP~400.
The repair removes every variant of the start and end parameters from the
supplied URL before applying its own window and swallows any leftover 400 rather
than failing. Back after 51.3\,s, it was still streaming at the snapshot, 395
points in.

\subsubsection{Header text in the data rows (spreadsheet, healed)}
A cultural-heritage workbook repeated its localized year header (\texttt{"Ano"})
down among the values, so the wrapper died on \texttt{int("Ano")}; the repaired
file quotes the exception, so the cause is recorded in the fix. The repair swaps
raw integer casts for coercing conversions and discards non-numeric rows, and the
same change turns up in three neighbouring wrappers mended the same night. Back
after 61.6\,s, it finished.

\subsubsection{A missing second column (CSV, not healed)}
A search-interest export came through as one column, leaving no
$(\textrm{time},\textrm{value})$ pair to find. Three repairs (27.0, 33.0, and
51.8\,s) tried delimiter sniffing and bad-line skipping, but none could conjure a
second column, and the loop stopped. A sibling wrapper reading a two-column
variant of the very same export healed on its first try. The manager mends code;
it cannot supply data the source withholds.

\subsection{Faults inside and outside the manager}
\label{sec:res-faults}
\input{tab_errors}
Table~\ref{tab:errors} sorts the \nErrorW{} wrappers that ended in \texttt{error}
by cause, and few of them indict the generated code. Fourteen never reached the
running stage: nine ran into the model's daily free-tier quota, one a per-request
rate limit, one a provider overload, and three more were cut off mid-generation
when a service restarted. Another, larger set of 54 are API pollers the 3600\,s watchdog stopped
between polling cycles, 53 of them leaving no traceback; here the watchdog is
just shorter than the source's daily or monthly rhythm, a setting mismatched to
the feed rather than broken code, and 48 of these had already delivered
52{,}372 points before being cut short. One wrapper crashed and could not be
mended because the repair call itself struck the quota ceiling, and that is the
lone error-status case where real generated code went unrepaired. The split is
the scope of control of Section~\ref{sec:scope} made concrete: code defects and
formatting quirks come off the operator's plate, while spent quota, bad
credentials, and limits set for the wrong cadence stay outside the managed
element and stay manual.

\subsection{Pipeline integrity and throughput}
\label{sec:res-pipeline}
Point counts thin out down the pipeline in a way that reconciles: the
\nDataPoints{} wrappers emit become 148{,}131 raw and then 106{,}442 consolidated
points in the resource store, and 100{,}550 points in the indicator store that
collapse, after chronological merging, into series of 84{,}431. The losses trace
to deleted resources (198 of \nWrappers{}, 126 of which left their wrapper
\texttt{stopped}), to regeneration wiping earlier data, to points landing for
resources with no indicator attached, and to timestamp-level deduplication at
merge time. Where we could check integrity, it held: across 30 days the collector
rejected nothing on schema grounds and raised only 18 duplicate-timestamp
warnings, each settled by averaging; over an 8.3-hour control-plane window the
resource service emitted 153 messages and the indicator service took in exactly
153, none lost in the broker; and the gateway handled 55{,}086 requests in about
20 days (near 2{,}750 a day, 80.3\% of them HTTP~200). Resumption proved itself in
the field: a container rebuild a few hours before the snapshot sent all 16
running wrappers through a restart, 15 of them continuing from stored watermarks
while the one missing a high watermark re-read its history from scratch.

\section{Discussion}
\label{sec:discussion}

Seen as an autonomic manager, the deployment explains both its successes and its
ceiling. Source-specific code stays out of human hands because generation is
fenced in by a fixed contract, because the plan is grounded in what the source
actually returns instead of what it is assumed to return, and because repair
fires on a genuine production trace. The ceiling is precisely the faults that sit
outside the managed element: the single error tied to unrepaired code was waiting
on a quota, and the single crash the loop could not mend was over data that was
not there.

The evidence has limits worth stating plainly. It is observational, drawn from
one deployment, one model family, and one region, with no side-by-side control;
the pre-automation period is a reference rather than a matched arm, and the crash
events are correlated, not independent. We have no hand-written wrappers for the
same sources to measure against, because none were ever built. We score a wrapper as
recovered once it runs cleanly again, which says nothing about whether the values
it extracts are right, since the collector inspects each batch's shape and never
the underlying truth; and for the healed wrappers the cause is read from the
repair because the relaunch destroys the trace, so the fault analysis
characterizes the model's fixes more than independently observed failures. A floating version alias pins the model, so
its underlying weights may have shifted across the run; the generation latency
includes queueing and so overstates model time; the memory figure is an idle
reading; and watermark coverage spans are computable for only the 11 wrappers
whose low mark was kept. Two systemic risks deserve their own mention and remain
open: the model quota is a single point of failure already behind 10 of the 69
terminal errors, and running model-written code as supervised production
processes is contained here only by the semaphore and watchdog, not by any
stronger sandbox. Whether the pattern carries beyond 396 wrappers and one region
is argued from its design, not demonstrated.

\section{Conclusion}
\label{sec:conclusion}

A smart city observatory turns source-agnostic once its wrappers look after
themselves. Treating each wrapper as the element of one MAPE-K manager pulls
three usually-separate behaviours into a single account: the manager plans a
wrapper from metadata and a sample, runs it as a supervised process that resumes
from its check-points, and re-plans it from production traces when it breaks, with
a shared knowledge base holding the fixed contract and the repair rules it has
accumulated. Across \deploymentDays{} days it kept \nWrappers{} wrappers and
\nDataPoints{} points flowing; of the \nRetried{} that crashed, all but one were
returned to a crash-free state by no more than three repairs, each a median
\healLatencyMedian{}\,s and with nobody in the loop. What it could not absorb was
environmental, which sets the agenda: checking extracted values for meaning, and
folding quota and credential faults into the manager as state it owns rather than
leaving them on an operator's desk.
