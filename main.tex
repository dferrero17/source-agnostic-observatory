\title{Operating LLM-Generated Data Wrappers in Production:\\
A 149-Day Case Study of What Breaks in a Smart-City Intake Layer}

% Anonymized for PRDC 2026 double-blind review. Fill in for camera-ready.

\maketitle

\begin{abstract}
A smart-city observatory lives or dies by intake: every indicator it shows needs a
wrapper that pulls one series from one heterogeneous source and keeps pulling it as
the source drifts, and the cost of writing and nursing those wrappers is what caps how
many feeds an observatory sustains. We report a \deploymentDays{}-day production case
study of an intake layer that removes the per-source code: a non-technical user
registers a source through a form, and the platform has a large language model write,
run, and repair the extraction wrapper, mapping REST APIs, spreadsheets, and CSV files
to a normalized $(\textrm{timestamp}, \textrm{value})$ series. Over \nWrappers{}
wrappers and \nDataPoints{} measurements the faults that bound the deployment were
operational, not generated-code defects: of \nErrorW{} terminal errors, 54 were kills
by an execution watchdog we had set shorter than the feeds' daily or monthly polling
period, 14 were model-provider faults (spent quota, overload, a mid-generation
restart), and one crashed wrapper went unrepaired because the repair call itself hit
the quota. Cheap generation decouples attempt from yield: only
\nNonzeroPointWrappers{} of \nWrappers{} wrappers ever produced data. Crash-triggered
repair restored execution for 42 of 43 crashed wrappers and resumed output for 32,
over a median post-repair exposure of \expMedianDays{} days, but two of four
inspected repairs recovered by swallowing an upstream error, so we score recovery as
resumed output and treat value correctness as open. We add a bounded estimate of
generation cost and a live re-extraction check on \spotN{} public sources. The
repair loop is established program repair and MAPE-K is only our lens; the
contribution is production evidence of where such a system breaks and what an
operator must still own.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Running a city on evidence means tracking many numbers at once, and those numbers
neither sit in one place nor arrive in one form. Environmental readings come off
sensor APIs, tourism figures from boards, energy and mobility counts from utilities
and transport operators, each with its own way in, a REST endpoint here, an Excel or
CSV export there, and its own field names, date formats, and language. None of it
stands still: an indicator earns its place only while it stays current, so every
feed must be pulled again and again, and every upstream change of format or endpoint
absorbed without breaking the series already built. The usual way to take a source
in is to write an extraction wrapper for it and then keep that wrapper alive as the
source shifts underneath. This cost, paid once per source to build and then
indefinitely to maintain, is why mediator-style integration has never reached past
a small set of feeds~\cite{wiederhold1992mediators,kushmerick2000wrapper,lerman2003wrapper},
and it sets the ceiling on coverage: an observatory ends up showing whichever feeds
someone found time to wire and to nurse, rather than the city.

Large language models can now write such wrappers from a description and a data
sample, and can rewrite them from a stack trace. That makes a different intake layer
possible, one where a domain user registers a source through a form and the platform
generates, runs, and repairs the wrapper itself. The engineering question is not
whether a model can write a wrapper, which benchmarks already
answer~\cite{arora2023evaporate,huang2024autoscraper}, but what happens when hundreds
of such wrappers run unattended in production for months: what breaks, whether the
failures indict the generated code or the environment around it, whether automatic
repair fixes faults or hides them, and what an operator is left holding. Those are
dependability questions, and they have no laboratory answer.

This paper is a case study that answers them for one deployment. \Sys{} (anonymized)
is a smart-city observatory for a European region whose intake layer is built from
LLM-generated wrappers. Each wrapper is an \emph{autonomic} element in the sense of
Kephart and Chess~\cite{kephart2003vision}, managed by a monitor--analyze--plan--execute
loop over shared knowledge (MAPE-K)~\cite{ibm2005blueprint,huebscher2008autonomic}
whose actuator is a model that writes code rather than a parameter tuner. We use that
loop only as a lens to organize the system and to name the boundary of what it can
fix; the loop itself is established LLM program repair, not our contribution
(Section~\ref{sec:related}). The adaptivity is bounded and we are explicit about it:
the platform adapts to a source's format and transport within the structured tabular
family, REST/JSON APIs, spreadsheets, and delimited files, all projected onto one
univariate $(\textrm{timestamp}, \textrm{value})$ series.

The contributions are the architecture and its one narrow contract
(Section~\ref{sec:arch}) and, mainly, the empirical findings from the
\deploymentDays{}-day run. First, the \emph{binding faults are operational, not
generated-code defects}: of \nErrorW{} terminal errors, 54 are kills by a watchdog
we configured shorter than the feeds' polling period, 14 are model-provider faults,
and the one error-status wrapper whose generated code went unrepaired was blocked by
a spent quota (Section~\ref{sec:res-faults}). Second, \emph{cheap generation
decouples attempt from yield}: only \nNonzeroPointWrappers{} of \nWrappers{} wrappers
ever produced data, shifting the bottleneck from authoring to triage of the silent
tail (Section~\ref{sec:res-gen}). Third, \emph{crash-triggered repair can mask faults
rather than fix them}, so we score recovery as resumed output, report the exposure
time over which repaired wrappers were observed, and treat value correctness as open
(Sections~\ref{sec:res-heal}--\ref{sec:res-cases}). We add a bounded estimate of
what generation cost and a live re-extraction check on the public sources still
reachable (Section~\ref{sec:res-cost}). The analysis script and a derived event
dataset accompany the paper.\coderepo

\section{Related Work}
\label{sec:related}

The smart-tourism literature argues for destination-scale data
infrastructure~\cite{gretzel2015smart,buhalis2013smart} and codifies indicators
through schemes such as ETIS~\cite{ec2016etis}, while field reports describe patchy
uptake~\cite{modica2018assessment}, dashboards assembled from warehouses and
surveys~\cite{fuchs2014big}, and getting the data in at all as the binding constraint
on sustained monitoring~\cite{ivarsbaidal2021measuring,ivarsbaidal2023sustainable}.
These accounts say little about how intake is built; we report one, from production.
The deployment is a tourism observatory, but nothing in the design ties it to tourism.

Autonomic computing proposed self-managing components with closed control loops
as the response to operational complexity~\cite{kephart2003vision}, structured as
MAPE-K~\cite{ibm2005blueprint} and catalogued by self-* property
family~\cite{huebscher2008autonomic}; a recent roadmap surveys generative models as
actuators in self-adaptive systems~\cite{li2024genaisas}. \Sys{} applies the
blueprint to data wrappers with a code-writing actuator, and we use the
correspondence to organize the exposition, not as a novelty claim.

Language models write runnable programs from prose~\cite{chen2021evaluating}, and
automated repair has moved to them too~\cite{xia2023automated}, closing a feedback
loop through self-critique~\cite{madaan2023selfrefine}, episodic
reflection~\cite{shinn2023reflexion}, or execution
results~\cite{chen2024selfdebug}, with inconsistent
benefit~\cite{olausson2024selfrepair}. Repair has run in production before: SapFix
and Getafix ship fixes at industrial scale~\cite{marginean2019sapfix,bader2019getafix},
and agentic repair drives the generate--run--observe--revise loop
autonomously~\cite{bouzenia2024repairagent}. On the data side, Evaporate showed
that synthesizing extraction code is cheaper at scale than calling a model per
record~\cite{arora2023evaporate}, AutoScraper builds reusable scrapers with an
agent~\cite{huang2024autoscraper}, agentic systems are benchmarked on enterprise data
workflows~\cite{lei2025spider2}, prompted~\cite{narayan2022wrangle} and
fine-tuned~\cite{zhang2024jellyfish} models handle preprocessing, and detecting
silent pipeline degradation is a line of work of its own~\cite{tu2023autovalidate}
that our masking finding motivates. \textbf{We make no novelty claim for the loop}:
the repair is LLM program repair, the generation Evaporate-style synthesis, the
probing ordinary tool use. What those systems do not provide, and what we
contribute, is a measured population of \emph{field} faults from a live deployment.

Wrapper induction derived extraction rules from labelled
examples~\cite{kushmerick2000wrapper} and later without
supervision~\cite{crescenzi2001roadrunner}, surveyed
in~\cite{laender2002brief,ferrara2014web}; keeping a wrapper working as its source
drifts was a distinct problem from the
start~\cite{kushmerick2000verification,lerman2003wrapper}. ETL pipelines have mostly
been designed by hand~\cite{vassiliadis2002conceptual,vassiliadis2009survey}, with
automation reaching schema matching~\cite{rahm2001survey},
curation~\cite{stonebraker2013tamer}, and wrangling~\cite{furche2016wrangling}.
Dataspaces~\cite{franklin2005dataspaces}, polystores~\cite{duggan2015bigdawg}, and
schema-on-read lakes make data source-agnostic for the \emph{consumer}; we work the
producer side, folding both the initial derivation and the later re-derivation of
each source's wrapper into LLM code generation.

\section{Architecture and the Fixed Time-Series Contract}
\label{sec:arch}

\Sys{} runs as a set of containerized services, user, knowledge-base,
data-collector, resource, and indicator (all Python and FastAPI), reached through an
nginx gateway with a React dashboard in front. Control traffic and data traffic
ride separate RabbitMQ brokers, each service keeps its own datastore, and an optional
Keycloak provider handles single sign-on. Fig.~\ref{fig:sysarch} lays out the
components and the two planes that join them, read top to bottom: the ingestion
plane, along which wrapper processes read the external sources and emit points
through the data broker to the collector and on to the indicator store, and the
REST serving plane through the gateway to the dashboard.

Format-adaptive intake rests on one deliberately thin interface. Whatever its
format, a wrapper emits point batches $\{(x,y)\}$ in which $x$ is an ISO~8601
timestamp and $y$ a floating-point value; the code above that interface is
generated per source, and everything below it is shared, fixed plumbing. The thin
contract is also the boundary: a source is in scope precisely when it can be
projected onto a single $(\textrm{timestamp}, \textrm{value})$ series. Out of scope
by construction are unstructured or scanned content, push and streaming transports,
multivariate, high-frequency, geospatial, and graph data, and anything that needs a
join across feeds; the unhealable single-column CSV of Section~\ref{sec:res-cases}
is this boundary made concrete. A user registers a source through a web wizard (a
file upload, or an API endpoint and its credentials) with the indicator's metadata;
the resource service then owns that wrapper for life, and downstream the collector
validates each batch against the contract before the indicator service stores,
merges, and serves the series. Source type is one argument to a single generation
routine, not a code path of its own.

\section{One Manager per Wrapper}
\label{sec:selfstar}

Each wrapper is the element a single autonomic manager looks after: the generated
code plus the state that travels with it, its execution watermarks, retry counter,
and status. The manager watches process state, classifies how a process ended, plans
a fresh or corrected artifact, and deploys it, against a shared store of knowledge.
Some of that knowledge is fixed: the wrapper template, which encodes the
Section~\ref{sec:arch} contract as code, and a standing list of fourteen hard rules
distilled from earlier failures (leave the backfill driver alone, invent no data,
treat date ranges as inclusive, keep timezone handling uniform, read localized month
names). The rest is per-wrapper and changes at runtime: a pair of watermarks (earliest
and latest timestamps sent), a retry counter capped at three, a timestamped execution
log, and the stored wrapper document with its metadata, source configuration, current
code, and status. The rule list is the part that grows: each diagnosed failure can add
a constraint every later plan must respect.

\subsection{Generation}
\label{sec:gen}
The actuator is Google's Gemini Flash, reached through the \texttt{google-genai} SDK
at default decoding settings and pinned to the floating \texttt{gemini-flash-latest}
alias. It does not write code freely but fills a fixed wrapper class: only extraction
(\texttt{fetch\_external\_data}) and, for APIs, a windowed fetch and a polling period
are open to it, while the backfill driver, transport, batching, and run loop are
library code the prompt tells it not to touch. Jinja2 assembles the prompt from the
indicator metadata, the source configuration, and a brief data sample (the opening 20
lines of a CSV, 15 rows per workbook sheet, or a captured API reply), alongside the
required output shape, the template, source-type instructions, and the rule list. For
an API the same call gives the model a sandboxed \texttt{fetch\_url} tool returning the
first 2500 characters of a live reply, which it may call up to fifteen times to learn
the response's nesting, field names, and date filters rather than guess them.
Authentication headers are built by the service from the declared scheme, so the
model never handles credentials. A static check gates deployment (the file parses and
no placeholder is left unfilled); a first failure earns one corrective prompt, a
second sends the wrapper to \texttt{error}. Nothing is executed as a test beforehand,
so any runtime fault is the repair loop's problem.

\subsection{Deployment}
\label{sec:deploy}
Deployment is ordinary process supervision, recorded only because it is what lets
the other loops run unattended. The resource service runs each wrapper as its own
operating-system process under a concurrency semaphore (default 100) and a per-run
watchdog (default 3600\,s). A file wrapper runs once; an API wrapper back-fills
history in size-adapting batches and then polls at the period its periodicity
implies, with no external scheduler. A monitor reads process state every 30\,s.
After a restart a wrapper resumes from its high watermark rather than re-fetching,
so a relaunch neither duplicates nor skips points, the same check-point-and-resume
idiom as streaming consumers.

\subsection{Repair}
\label{sec:heal}
The 30\,s monitor reads each process's exit status. An abnormal exit, in practice
always code~1, is separated from a watchdog kill and from a provider error during
generation, and only the first becomes a repair. The plan is one model call carrying
the full crashed source, its captured stderr, and the final twenty lines of stdout,
with the instruction to return a complete corrected file that preserves the class and
addresses that traceback; for an API wrapper it may re-interrogate the endpoint
through the same \texttt{fetch\_url} tool, up to ten times. The returned file passes
the same static check, replaces the old one, bumps the retry counter, and the process
is relaunched from its watermarks. At most three repairs are granted; the fourth-time
loser stays in \texttt{error} for a person. Because the trigger is a live exit code
that may arrive weeks after generation, the feedback carries the source's real
behaviour rather than a test author's guess, and because the plan re-emits the whole
wrapper, a repair can re-shape the extraction end to end instead of touching one
statement~\cite{chen2024selfdebug,olausson2024selfrepair}.

\subsection{Scope of control}
\label{sec:scope}
The same view marks the limit of the manager's reach, and we draw it operationally
before looking at the counts: a fault is \emph{inside} the manager when a change to
the wrapper's code can fix it (broken extraction logic, a source's formatting quirks),
and \emph{outside} when the fix lies in something the code cannot rewrite (a spent
model quota, a stale credential, a platform watchdog set shorter than a source's
polling period). The boundary is a design choice, not a law: the watchdog and the
polling period are both values the platform sets, so a cadence mismatch is outside the
loop only because we left interval-setting outside it. Section~\ref{sec:res-faults}
asks how the production faults fall relative to that line.

\section{Production Case Study}
\label{sec:results}

The figures come from a \deploymentDays{}-day run (\deploymentStart{} to
\deploymentEnd{}) captured as one complete state snapshot: the wrapper collection
(\nWrappers{} documents with generated code and execution logs), the per-wrapper
logs, the resource and indicator stores, the service logs, and container statistics.
Every number below is computed from that snapshot by the released script. At the
snapshot the deployment spanned 17 containers and about 2{,}082\,MiB of resident
memory while idle; the resource service, host to every wrapper process, was the
heaviest at 682\,MiB.

\subsection{Generation and yield}
\label{sec:res-gen}
The manager produced \nWrappers{} wrappers, \nXLSX{} for spreadsheet sources,
\nAPI{} for APIs, and \nCSV{} for CSV, over three domains (environment
\nDomAmbiente{}, economy \nDomEconomia{}, sociocultural \nDomSocio{}); between them
they collected \nDataPoints{} points (\nDataPointsXLSX{} from spreadsheets,
\nDataPointsAPI{} from APIs, \nDataPointsCSV{} from CSV). Volume is long-tailed: the
median wrapper contributed \medianPointsPerWrapper{} points and the 90th percentile
\pNinetyPointsPerWrapper{}, with \nNonzeroPointWrappers{} of \nWrappers{} sending at
least one. The time from a generation request to the first running process had a
median of \genLatencyMedian{}\,s and a 90th percentile of \genLatencyPninety{}\,s
over \nGenLatencySamples{} wrappers, a figure that folds in queueing, sampling, the
model call, and the static check. Downstream, 118 of the 179 active indicators are
tied to a source and 111 carry data through the whole pipeline; the busiest live
series is an hourly air-quality feed at 20{,}069 points, and backfill reaches the year
2000 for the 11 feeds whose lower watermark was retained. Cheap generation comes with
a long silent tail: \nZeroPointWrappers{} wrappers delivered no data, 69 with a
since-deleted resource, 20 that never ran (quota or watchdog), 22 that completed yet
found nothing usable, and 1 still executing, so scaling coverage shifts the cost from
authoring wrappers to triaging this tail. Outcomes by source type appear in
Table~\ref{tab:status}, and the status machine with production counts in
Fig.~\ref{fig:lifecycle}.

\subsection{Repair effectiveness and exposure}
\label{sec:res-heal}
\nRetried{} wrappers (\pctRetried\%; 26 spreadsheet, 14 API, 3 CSV) threw an
uncaught exception while running and were taken up by the repair loop, which shipped
\nHealEvents{} redeployments; per wrapper the repair depth was \retryOnce{} at one
attempt, \retryTwice{} at two, and \retryThrice{} at three. ``Recovery'' can be read
three ways that do not agree, so we keep them apart and rank them. The weakest
reading is recurrence: the same crash came back after the last repair for exactly one
of the 43, so 42 stayed crash-free. Final status is the next: \nRecovered{} of 43
(\pctRecovered\%) closed in a non-error state, a count that still includes the one
wrapper that burned all three attempts and shows non-error only because its resource
was deleted afterwards, which we do not score as a win. The reading we adopt as
primary is resumed output: 32 of 43 sent data again after their last repair, 20{,}351
points in all, about an eighth of everything collected, though one test feed accounts
for 17{,}466 of them. Repairs were fast and untouched by a person: a median
\healLatencyMedian{}\,s from crash to redeployment (quartiles 24.2 and 50.8\,s, 90th
percentile \healLatencyPninety{}\,s, longest \healLatencyMax{}\,s), up to 30\,s of
which is the detection cycle. The typical crash arrived 16.8\,s into a run, in the
fetch-and-parse stage.

A wrapper observed only briefly after its repair has had little chance to fail again,
so recurrence and resumed output are only as strong as the exposure behind them. We
therefore measured, for each repaired wrapper, the time from its last repair to its
last evidence of life (last log entry or emitted point, or the snapshot for wrappers
still executing): the median is \expMedianDays{} days (quartiles \expQone{} and
\expQthree{}, range \expMinDays{}--\expMaxDays{}), \expUnderDay{} wrappers had under a
day of exposure and \expOverWeek{} more than a week, and the 42 crash-free wrappers
accumulate \expWrapperDays{} wrapper-days without a recurrence. Wrappers whose
resource was deleted soon after repair are counted at their deletion, which is why
the short-exposure group exists; their ``recovery'' is unverified rather than
confirmed.

Two features of the timeline qualify the counts further. For the first 65 days no
repair loop was active (it first appears in the logs on 2026-03-19), and over that
stretch 36 crashes of the same exit class were left to die; we read the comparison
descriptively, since the early period differs in source mix and load and is not a
matched control. And 31 of the 50 repair events land on a single day, when a
credential fix set off a redeploy that restarted every wrapper together, so the events
are correlated rather than 50 independent failures. The latency is unaffected:
restricted to each wrapper's first repair, the 17 that first crashed on other days
have a median 34.0\,s (range 15.5--80.4) against 33.2\,s for the 26-wrapper batch, and
15 of those 17 independent crashes ended non-error, an 88\% rate in line with the
pooled \pctRecovered\%. Because each relaunch overwrites stderr, a triggering trace
survives only where the last run also crashed; for recovered wrappers we read the
cause from the fixes their code carries, so these counts describe the model's
\emph{repairs}, not independently observed causes.

\subsection{Faults inside and outside the manager}
\label{sec:res-faults}
\input{tab_errors}
This is the paper's central result: the binding faults are operational, not
generated-code defects. Table~\ref{tab:errors} sorts the \nErrorW{} wrappers that
ended in \texttt{error} by cause, and few of them indict the generated code. Fourteen
never reached the running stage: nine ran into the model's daily free-tier quota, one
a per-request rate limit, one a provider overload, and three were cut off
mid-generation when a service restarted. The larger set of 54 are API pollers the
3600\,s watchdog stopped between polling cycles, 53 of them leaving no traceback. We
are explicit about what this is: a platform setting of our own, an execution timeout
shorter than the feeds' daily or monthly rhythm, so these are configuration faults
in the operational envelope, not environmental accidents and not code defects; 48 of
the 54 had already delivered 52{,}372 points before being cut short. One wrapper
crashed and could not be mended because the repair call itself struck the quota
ceiling, the lone error-status case where generated code went unrepaired. The
lesson is about the workload, not just the loop: once generation is cheap, code
defects grow rare relative to the operational envelope of quota, credentials,
service availability, and cadence-to-timeout matching. The specific watchdog and
free-tier quota are this deployment's instantiation; the category is what we expect
to transfer. The split makes the scope of control concrete: code defects and
formatting quirks come off the operator's plate, while quota, credentials, and
mismatched limits stay outside the managed element and stay manual. The manager
removes the per-source \emph{code}, not every per-source decision.

\subsection{Repair case studies}
\label{sec:res-cases}
Four wrappers, chosen to exercise the boundary rather than sampled at random, put
faces on the partition. A yearly urban-waste API wrapper crashed 82\,s into its
backfill on a timezone-aware-versus-naive comparison; the repair normalizes both
bounds and downgrades an empty fetch to a log line (back in 34.7\,s, 596 points). An
air-quality wrapper whose configured URL already pinned a date window had a second
one appended and got an HTTP~400; the repair strips the duplicate parameters and
swallows any residual 400 (51.3\,s, 395 points, still streaming). A cultural-heritage
workbook repeated its year header (\texttt{"Ano"}) among the values, so the wrapper
died on \texttt{int("Ano")}; the repair coerces to numeric and drops non-numeric
rows, a fix three sibling wrappers received the same night (61.6\,s). The
out-of-scope case is a search-interest export that arrived as a single column: three
repairs tried delimiter and bad-line tricks but could not invent a
$(\textrm{time},\textrm{value})$ pair, while a two-column sibling healed on the first
try. Two of the four ``heal'' by absorbing an upstream error rather than extracting
the intended data, which is exactly the move that can mask data loss behind a clean
exit; the manager mends code, and it cannot supply data the source withholds.

\subsection{Cost, and a live check on values}
\label{sec:res-cost}
The platform logged no token counts, so generation cost is an estimate we label as
such. From the prompt-assembly templates and the stored wrappers we measured the
fixed prompt (template, rules, instructions), the variable sample, and the generated
code, converting characters to tokens at four per token, and priced them at the
published Gemini Flash rates on \costPriceDate{} (\costInPrice{} and \costOutPrice{}
USD per million input and output tokens); tool replies during API probing are bounded
above by fifteen calls of 2500 characters. A generation costs about
\costGenMedianUSD{} USD at the median and a repair about \costRepairMedianUSD{} USD,
so the \nWrappers{} generations and \nHealEvents{} repairs together cost on the order
of \costTotalUSD{} USD in model calls. No hand-written wrapper was ever built for the
same sources, so the saving over manual authoring is plausible but unmeasured; what
the estimate does establish is that model cost is not the binding constraint, and
that the free-tier quota, which caused 11 terminal errors, bit long before cost did.

The collector checks each batch's shape, not whether the values match the source,
and the snapshot retains no copy of the sources, so value correctness could not be
verified from the dump. As a bounded substitute we took the stored code of
\spotN{} API wrappers whose endpoints are public and need no credential, re-ran only
their extraction logic against the live source at the time of writing, and compared
the fresh $(\textrm{timestamp},\textrm{value})$ pairs with the dumped points over the
overlapping range: \spotReachable{} sources were still reachable, yielding
\spotOverlap{} overlapping timestamps of which \spotMatch{} matched exactly and
\spotMismatch{} did not. This is a small, convenience-sampled check on the sources
that happen to be public and stable; it is the first ground-truth evidence for the
deployment and no more than that.

\subsection{Pipeline integrity}
\label{sec:res-pipeline}
Point counts thin out down the pipeline: of the \nDataPoints{} points the wrappers
emit, 148{,}131 reach the resource store as raw segments and 106{,}442 survive
consolidation, 100{,}550 land in the indicator store, and chronological merging
leaves series of 84{,}431. The losses trace to deleted resources (198 of
\nWrappers{}), to regeneration wiping earlier data, to points landing for resources
with no indicator attached, and to timestamp-level deduplication at merge time.
Where we could check integrity, it held: across 30 days the collector rejected
nothing on schema grounds and raised only 18 duplicate-timestamp warnings; over an
8.3-hour control-plane window the resource service emitted 153 messages and the
indicator service took in exactly 153. Resumption proved itself in the field: a
container rebuild a few hours before the snapshot sent all 16 running wrappers
through a restart, 15 of them continuing from stored watermarks while the one missing
a high watermark re-read its history from scratch.

\section{Discussion and Threats to Validity}
\label{sec:discussion}

For a city scaling an indicator observatory the findings carry into operations.
Since the binding faults are operational, coverage grows by governing quotas,
credentials, and cadence-to-timeout matching rather than by chasing a better code
generator; cheap generation moves the bottleneck off authoring and onto operations,
and the watchdog mismatch in particular is a fault the platform could fold into the
manager by letting the generated polling period set the timeout. Since attempting a
feed is nearly free, an observatory can take on the long tail of feeds it once
skipped, but must budget for triaging the silent majority that never yields. And
since repair can mask data loss, a dashboard may show a healthy wrapper that has
silently stopped delivering, a trust hazard when the series inform policy, so
value-level monitoring is a first-class need, not an afterthought.

The evidence is observational, from one deployment, one model family, and one
region, with no side-by-side control; the pre-automation period is a reference
rather than a matched arm, the crash events are correlated, and no hand-written
wrappers exist for the same sources. The cost figure is an estimate, not a
measurement. We score recovery as resumed output, and the exposure analysis shows
how much observation backs that score, but the collector inspects shape and never
truth; the live check covers only the public, stable sources. For repaired wrappers
the cause is read from the fix because the relaunch destroys the trace, so the fault
analysis characterizes the model's repairs more than independently observed
failures. The model is pinned only through a floating alias, so the exact numbers may
reflect weight changes mid-run and are not reproducible against a fixed model. We do
not ablate tool-assisted probing, the template constraint, or whole-file repair, so
their value is argued from design; and because the source mix is user-selected and
the fourteen rules accreted over the run, the low rate of code defects is partly
co-produced by human curation. Whether the pattern carries beyond \nWrappers{}
wrappers and one region is argued from its design, not demonstrated. Two operational
risks are real: the model quota is a single point of failure, and model-written code
runs as live processes contained only by per-process isolation, a semaphore, and the
watchdog, while the generation prompt ingests a live sample of the source, an
untrusted-input path we did not harden against prompt injection.

\section{Conclusion}
\label{sec:conclusion}

We operated LLM-generated extraction wrappers as live infrastructure for
\deploymentDays{} days: \nWrappers{} wrappers, \nDataPoints{} points, and of the
\nRetried{} that crashed, all but one stayed crash-free after at most three
unattended repairs, 32 resumed delivering data, and repair took a median
\healLatencyMedian{}\,s. The result we stand behind is empirical: in production the
faults that bind are operational, a timeout we set, a quota we exhausted, a provider
that was down, not defects in the generated code, and the repair loop governs exactly
the code the model owns. What it could not absorb sets the agenda: checking extracted
values for meaning, and folding cadence, quota, and credential faults into the
manager as state it owns rather than leaving them on an operator's desk.
